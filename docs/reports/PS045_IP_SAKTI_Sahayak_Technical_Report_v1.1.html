1Executive Summary

IP-SAKTI Sahayak is a decision-support web application that helps Ayurveda innovators, researchers, startups and IP/regulatory professionals investigate a single question from several angles at once: what does the available evidence actually say about this innovation’s intellectual property position, scientific backing, traditional-knowledge context and regulatory pathway, in a given jurisdiction? It is built around one architectural discipline, carried through every module: nothing is asserted that was not first retrieved from a cited source, and nothing is shown as supported without a passage-level verification pass.

In plain terms. Imagine typing a question like “can I patent a stress-relief tablet made from Ashwagandha and Turmeric, and what rules apply in India?” Instead of guessing an answer the way a general chatbot would, this system first searches a library of real laws, patents and studies, only writes an answer using what it actually found, double-checks every sentence of that answer against the source it came from, and says “I don’t have enough evidence” rather than making something up when it isn’t sure. It does this separately for India, the USA and Australia, since the rules differ in each. The rest of this report explains, section by section, exactly how much of that is real and working today versus still a work in progress — nothing is overstated.

The current repository is a working full-stack application (a complete product with both the part users see and the part that runs behind the scenes): a Next.js 15 frontend, a FastAPI backend with 108 distinct API routes across 9 routers, a PostgreSQL 16 database (29 tables) with the pgvector extension for dense retrieval, and a hybrid retrieval pipeline that combines vector search, PostgreSQL full-text search, metadata filtering and graph expansion with deterministic reranking. A separate, server-enforced Admin Console sits alongside the user application with its own login, session scope and role check on every request. 69 automated backend tests exercise authentication/RBAC, retrieval correctness, citation verification, jurisdiction isolation, safety abstention, and a full end-to-end user journey.

This report is written to the standard the problem statement demands: every capability is labelled with its real implementation status (Implemented / Partial / Mock / Planned / Not Measured), PS-045’s explicit requirements are kept visibly separate from engineering work added beyond them, and no performance, accuracy or corpus figure appears anywhere in this document unless it was read directly from the running system or the source code during preparation of this report.

Headline honesty note. The corpus behind this system is a curated seed set — 39 documents, 13 sources, 81 chunks (measured live via GET /api/admin/metrics at report time) — not a production-scale knowledge base, and several demo patents and two guidance notes are explicitly fictional and labelled as such in the product itself. Default embeddings are an offline hashing scheme, not a trained semantic model, unless reconfigured. These facts are expanded in §15, §36 and §48, and are stated here first because they materially bound every other claim in this report.

2Problem Statement

Ayurveda innovation sits at the intersection of four domains that are each individually complex, and whose combination is where most real decisions actually fail:

  • Intellectual property — an Ayurvedic formulation’s patentability is shaped by exclusions specific to traditional-knowledge-derived inventions (e.g. India’s Patents Act §3(p), the Biological Diversity Act’s NBA approval requirement), which a generic patent search tool has no concept of.
  • Traditional knowledge — TK context carries attribution, access and disclosure obligations that differ from ordinary prior art, and restricted repositories (e.g. TKDL) cannot legally or practically be scraped by a side project.
  • Scientific evidence — a study on an isolated ingredient (e.g. an Ashwagandha extract) does not automatically support a claim about a multi-ingredient finished formulation; conflating the two is a common and consequential error.
  • Regulatory classification — the same formulation can be a classical ASU medicine, a patent/proprietary ASU medicine, a food, or a health supplement depending on positioning and claims, under different frameworks in India (AYUSH/CDSCO/FSSAI), the USA (FDA/DSHEA) and Australia (TGA), which must never be silently blended together.

Overlaying all of this is a language and access problem: much of the relevant literature and regulation is in English, but the people best placed to judge traditional context often work in Hindi; and across all of the above, the cost of a wrong but confident answer is high, while the cost of an honest “insufficient evidence” is low. A generic conversational AI model, prompted with general knowledge, will readily produce fluent, specific-sounding answers to exactly these questions — with no mechanism to say when it does not actually know, no binding between a claim and the passage that is supposed to support it, and no concept of jurisdiction boundaries. That is the gap PS-045 targets: not better chat, but evidence discipline applied to a genuinely cross-domain problem.

3Proposed Solution

IP-SAKTI Sahayak’s answer is to make every module share one evidence pipeline rather than reasoning independently, and to route every user-facing claim through the same retrieve→verify→label discipline regardless of which module produced it.

Innovation │ ▼ Structured Innovation Profile (ingredients, process, claims, target jurisdictions) │ ├──► Traditional Knowledge Context (public/authorised only, access-limited) ├──► Scientific Evidence (ingredient- vs formulation-level, separated) ├──► Patent / Prior-Art Intelligence (jurisdiction-scoped matching, never a verdict) └──► Regulatory Intelligence (per-jurisdiction classification + pathway) │ ▼ Citation Verification (every claim bound to a passage, checked, scored) │ ▼ Evidence Gaps (what is still missing, by severity) │ ▼ Human Escalation (packet handed to a named reviewer, audited)

4Objectives

  • Evidence-grounded answers to IP, regulatory, scientific and TK questions
  • Source citations on every substantive claim
  • Structured innovation profiling from a free-text description
  • Patent / prior-art discovery scoped to the innovation’s own target markets
  • Scientific evidence discovery that separates ingredient- from formulation-level support
  • Jurisdiction-specific regulatory classification and pathway guidance
  • Multilingual interaction (English / Hindi)
  • Explicit citation verification, not just citation display
  • Safe abstention when evidence is missing, conflicting or out of scope
  • Human escalation with a complete evidence packet
  • End-to-end auditability of user and admin actions

Technical Objectives

  • Hybrid retrieval (dense + lexical + metadata + graph) over a relational store, avoiding a second database system
  • Deterministic, explainable reranking (not an opaque learned ranker)
  • A pluggable LLM provider layer that degrades to extractive-only output rather than failing when no key is configured
  • Hard server-side enforcement of workspace isolation and role checks, not just UI hiding
  • A fully separate admin session scope, re-checked on every request
  • Secure handling of confidential innovation data (hashing, validation, upload sanitisation)
  • A real automated test suite covering security-critical paths, not just happy paths

9Frontend Architecture

The frontend is a Next.js 15 App Router application with three route trees: public pages, the authenticated user application (/app/**), and a fully separate authenticated admin console (/admin/**) that never shares session state with the user app (two distinct React context providers — lib/providers.tsx’s useApp() and lib/admin.tsx’s useAdmin() — and two distinct session cookies). State management is deliberately minimal: TanStack Query for server state, React Context for session/language/workspace/jurisdiction preference, and localStorage for client-only persistence — no Redux/Zustand.

16Innovation Profiler

A 7-step wizard (frontend/app/app/innovations/new/page.tsx) collects: basic info (name, description, intended use), ingredients (common/Sanskrit/Hindi/botanical/chemical name, extract, quantity, source), formulation, process (extraction/manufacturing), claims, target markets (multi-select IN/US/AU — the authoritative field, stored as Innovation.target_markets), and confidentiality level. Submission calls POST /api/innovations, which builds a structured InnovationProfile and a set of typed InnovationFeature rows (ingredient/composition/process/extraction/delivery/dosage-form/claim/use/manufacturing/other).

Profile generation explicitly flags rather than silently resolves ambiguity — e.g. a common name like “Brahmi” maps to two distinct botanical species (Bacopa monnieri or Centella asiatica) and is surfaced to the user as an open question, not auto-picked. A disease/treatment claim in free text is also flagged, since it changes the regulatory analysis materially. The profile and its target markets are what every downstream module (patents, regulatory, gaps) reads — there is no second, independent “jurisdiction” or “markets” field elsewhere that could silently diverge. Status: Implemented, end-to-end tested (tests/test_integration_flow.py).

18Traditional Knowledge Context

TK-related documents in the corpus (ABS/disclosure law excerpts, TK context notes) are retrieved through the same hybrid pipeline, scoped to the TK_ABS domain. Access level on each TK-tagged source is explicit (PUBLIC / RESTRICTED_RECORDS_PUBLIC_INFO / WORKSPACE / RESTRICTED); documents marked RESTRICTED are excluded from retrieval entirely at the SQL layer (d.access_level <> 'RESTRICTED' is a hard clause in every retrieval query). A dedicated evidence gap (nba-approval) is raised whenever an innovation targets India or sources an ingredient from India, pointing at the Biological Diversity Act’s NBA approval requirement. Status: Implemented for the mechanism; Mock/limited for underlying TK content, since there is no restricted-database integration by design.

19Scientific Evidence

Scientific retrieval is intentionally jurisdiction-agnostic (science doesn’t belong to a country) but is not ingredient/formulation-agnostic: every ScientificStudy record carries an evidence_level of INGREDIENT or FORMULATION, and the scientific-evidence view explicitly states, for every ingredient-level card, that it does not establish efficacy of the finished multi-ingredient formulation — this distinction is enforced in code (services/analysis.py) and asserted in the test suite, not left to prose. The seed corpus contains 6 scientific studies, all ingredient-level (Ashwagandha, Turmeric/curcumin, Triphala) — there is currently no finished-formulation-level study in the corpus, which the gap-detection logic surfaces as a formulation-evidence gap by default. Status: Implemented mechanism, Mock/limited underlying data.

21Jurisdiction Engine

Three jurisdictions are supported: India, USA, Australia. Selection happens on the landing page (a multi-select, persisted via a shared client-side preference mirroring the existing workspace-selection pattern) and is carried automatically through registration/login into the dashboard, chat assistant and research forms — not re-asked on every page. At the innovation level, Innovation.target_markets is the authoritative per-innovation override, feeding regulatory classification, evidence-gap detection, and (as of this report) patent matching.

Jurisdiction is enforced, not cosmetic, at the retrieval layer: a hard SQL filter restricts results to the selected jurisdiction(s) plus international instruments, and a reranking term boosts jurisdiction-matching results further. A dedicated JURISDICTION_COMPARISON intent runs fully separate retrieval per jurisdiction rather than one blended query. If a user asks about a jurisdiction other than the one currently selected, the system detects the mismatch and asks for clarification rather than silently answering with the wrong jurisdiction’s rules. If evidence for the selected jurisdiction is insufficient, the system says so explicitly rather than filling the gap from another jurisdiction. Admin analytics (RAG and citation monitoring) break activity down by jurisdiction. Status: Implemented, with 9 dedicated backend tests covering filter correctness, gap parity (India/USA/Australia), and the admin analytics rollups.

22Multilingual Architecture

Supported UI languages: English and Hindi — matching the PS-045 MVP target exactly; no other language is implemented. Hindi queries are handled primarily via terminology expansion over the English-language corpus (Sanskrit/Hindi/botanical/chemical name mapping), not via a parallel Hindi corpus or Hindi-trained embeddings. When an LLM is configured, Hindi questions can additionally be answered in Hindi and Hindi queries can be translated for retrieval — with an explicit guard that rejects an LLM “translation” that is implausibly long or that invents a named legal instrument not present in the original query (added specifically after an observed hallucination of a fictitious “Traditional Knowledge Digital Library Act, 2005”). OCR supports Hindi text extraction when the Tesseract Hindi language pack is installed. Status: Implemented for EN/HI UI and terminology-based retrieval; Partial for LLM-based Hindi generation/translation (provider-dependent, with a demonstrated past failure mode now guarded against rather than eliminated by design).

This is deliberately not a cosmetic “show a source link” feature: the system reconstructs its final displayed answer only from sentences that survive verification against the retrieved passages, and drops/reports the rest in a limitations field rather than showing unverified prose. An LLM-reported verdict string is validated against an allowed set before being trusted — a malformed or out-of-vocabulary value from the model is ignored rather than acted on. 24Evidence Graph

Per innovation, a graph is constructed (services/analysis.py::evidence_graph()) with first-class node types for Innovation, Feature, Evidence, Regulation, and Jurisdiction (jurisdiction is a real node type, not a label on an edge), with provenance retained on every edge back to the originating passage. The frontend renders this as an interactive node/edge diagram using React Flow (@xyflow/react) on the /app/innovations/[id]/graph tab. Status: Implemented.

25Safety & Abstention

The governing principle, enforced in code rather than only stated in a prompt: do not guess when evidence is insufficient. Concretely implemented gates:

  • Insufficient evidence → explicit INSUFFICIENT status with what was searched and what is missing
  • Conflicting sources → shown side by side, never silently merged
  • Jurisdiction not selected / detected → clarification request, not a guess
  • Jurisdiction outside IN/US/AU → explicit refusal (e.g. EU questions)
  • Outdated/superseded sources → freshness-labelled (Current / Recently checked / Potentially stale / Superseded / Unknown), excluded unless explicitly requested
  • Unsupported claims → dropped from the final answer, not merely flagged
  • Medical/legal-certainty questions → explicit boundary refusal (this is not a medical or legal determination)
  • Restricted-TKDL-style requests → explicit refusal, not a best-effort answer
  • Prompt injection in the query or in retrieved documents → detected and never followed

Status: Implemented, each gate covered by at least one dedicated test in tests/test_rag.py.

26Human-in-the-Loop / Escalation

Four escalation types exist (IP_REVIEW, REGULATORY_REVIEW, DOMAIN_REVIEW, HUMAN_REVIEW), each created with a full evidence packet (profile, findings, gaps, citations, open questions, audit trail) attached, not just a note. Escalations carry a status workflow (OPEN→IN_REVIEW→RESOLVED→CLOSED) and, in the admin console, can be assigned to a named reviewer with accumulating reviewer notes. Evidence gaps above a severity threshold are a direct trigger surfaced to the user for escalation, not merely logged. Status: Implemented, end-to-end tested.

Two independent RBAC layers exist: a global User.role (ADMIN/USER) that only gates the separate admin console, and a per-workspace WorkspaceRole (OWNER>ADMIN>RESEARCHER>REVIEWER>VIEWER) that gates actions inside the app — an ADMIN-role user gets no special workspace privileges merely by being a global admin; they must also hold a workspace role, same as anyone else. 29Privacy & Confidentiality

33AI / LLM Architecture

An LLMProvider abstract base class is implemented once (OpenAICompatibleProvider) and parameterised per provider: ollama (local, free, private — the default in this deployment’s .env), gemini, groq, grok, openai, deepseek, plus a mock fallback (the default in the committed .env.example, i.e. a fresh checkout with no key configured runs in extractive-only mode by default). There is no agent framework, no tool-calling/function-calling orchestration, and no multi-agent system — the LLM is called directly for two purposes: answer generation (constrained to the assembled retrieved context) and, when configured, a capped claim-entailment check (at most 3 LLM calls per answer, for cost/latency control). System prompts explicitly instruct the model to answer only from the provided context, to never follow instruction-like text found inside retrieved content, and to mark uncertainty rather than invent specifics. If the configured provider fails at runtime, the system falls back to extractive mode automatically and states so in the answer rather than erroring out.

36Evaluation Framework

An evaluation harness exists (services/evaluation.py, EvaluationQuestion/EvaluationRun tables, POST /api/admin/evaluations/run): a seeded set of gold questions (with expected abstention/keywords/source titles per question) is run against the live pipeline, with baselines for comparison (BM25-only, always-answer, LLM-only-without-retrieval) and classification-agreement scoring. This is a genuine evaluation mechanism, not a mock — but its outputs are whatever the last admin-triggered run produced against the current small seed corpus; there is no continuously tracked, externally validated benchmark result to report.

37Performance & Scalability

No load test, benchmark, or production traffic has been run against this deployment; the live /api/admin/metrics endpoint (queried for this report) reports zero sampled queries and null latency in its current window. Architecturally: retrieval and reranking run in-process inside the FastAPI worker (CPU-bound SQL queries, no external compute), embeddings default to an offline hashing scheme (no network call, effectively free but semantically weak), and background ingestion jobs run as FastAPI BackgroundTasks within the same process rather than a separate worker pool — appropriate for the current small corpus, but a self-acknowledged limitation for larger ingestion volume. Rate limiting is in-process, so correctness under multiple server instances is not guaranteed without a shared store. Status: Not Measured (no benchmark), architecture reviewed as Prototype-scale.

38Deployment Architecture

Local/single-machine deployment is fully scripted: Docker Compose brings up PostgreSQL (pgvector/pgvector:pg16); a backend Dockerfile and frontend Dockerfile exist for containerised builds; a one-command script (scripts/start_all.sh) additionally handles local Ollama startup/model preload, Alembic migration, seeding, and launching an ad-hoc public HTTPS tunnel (Cloudflare quick tunnel) for demonstration purposes. There is no committed Kubernetes manifest, no cloud infrastructure-as-code, no managed-database configuration, and no CI/CD pipeline of any kind. The demonstration public URL is explicitly ephemeral (tied to one machine staying powered on) and is not a production hosting arrangement. Status: Implemented for local/Docker deployment; Not Implemented for any managed/cloud production deployment path.

47What Has Actually Been Built

If the current repository is run today, what does the software actually provide? A working, locally-deployable full-stack web application: a user can register, select a jurisdiction, describe an Ayurveda innovation in free text, receive a structured profile with flagged ambiguities, ask the AI Research Assistant jurisdiction-aware questions and receive citation-verified answers (or an honest abstention), see scientific evidence correctly separated by ingredient vs. formulation level, see a jurisdiction-scoped patent/prior-art matrix, get a provisional regulatory classification and passport across India/USA/Australia, see computed evidence gaps and a risk map, inspect an interactive evidence graph, generate an exportable evidence report, and raise a human escalation with a full packet. In parallel, an administrator — through a fully separate, server-enforced console — can curate the source/document corpus, monitor retrieval and citation quality (including per-jurisdiction), run the evaluation harness, manage users and workspaces, triage escalations and feedback, and audit every action. All of this is backed by a real Postgres database with 29 tables, 108 API routes, and is exercised by 69 passing automated tests. What it does not provide, as of this report: a production-scale verified corpus, published accuracy/latency benchmarks, a CI/CD pipeline, or a cloud deployment — these are stated plainly in §48.

48Limitations

  • Corpus is a curated seed set: 39 documents, 13 sources, 81 chunks (30 real/9 demo-fictional) — not a production knowledge base
  • Patent coverage is thin and uneven across jurisdictions (3 IN / 2 US / 1 AU / 1 EP), all fictional
  • Scientific evidence is ingredient-level only (6 studies); no finished-formulation-level study exists in the corpus
  • No TKDL or other restricted traditional-knowledge database access, by design
  • Only 3 jurisdictions supported (India, USA, Australia); all others explicitly refused, not approximated
  • Only 2 languages supported (English, Hindi); Hindi retrieval relies on terminology expansion, not a native Hindi corpus
  • Default embeddings are offline hashing, not a trained semantic model (semantic embeddings are available but not the default)
  • LLM generation is provider-dependent; with no provider configured, answers are extractive quotes, not synthesis
  • No published precision/recall/latency benchmark; queries_sampled: 0 in the live metrics endpoint at report time
  • Rate limiting is in-process, not safe across multiple server instances
  • Background jobs run inline in the request process, not on a dedicated worker queue
  • No CI/CD pipeline; the 69-test suite is not automatically enforced on every change
  • No frontend automated test suite or committed browser-regression suite
  • No cloud/production deployment path (Docker Compose + a local-machine demo tunnel only)
  • No third-party security audit or compliance certification held or claimed

49Future Roadmap

The items below are proposals for future work. None are implemented today; they are listed separately from §40–§47 specifically so they are never mistaken for current capability.

  • Expand the verified document corpus, especially patent and formulation-level scientific coverage
  • Add jurisdictions beyond India/USA/Australia with the same hard-isolation discipline already proven for the current three
  • Move the default embedding provider to a trained semantic model and reseed
  • Add a cross-encoder or learned reranking stage
  • Integrate additional verified source feeds (patent office APIs, regulator publication feeds)
  • Build a repeatable, published evaluation benchmark (retrieval + generation + safety metrics) run on a schedule, not only on demand
  • Stand up a CI/CD pipeline running the existing 69-test suite (and a new frontend suite) on every change
  • Move rate limiting and background ingestion to shared infrastructure (e.g. Redis, a worker queue) for multi-instance deployment
  • Add a cloud deployment target with managed Postgres/pgvector and observability
  • Commission an independent security review before handling real confidential innovation data at scale
